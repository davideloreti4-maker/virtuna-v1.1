Merged landing + the run bar

Sketch, 2026-08-08 · lane/platform-concept. Covers the run model, the merged landing, the selector row, the skill map, what survives from the old dashboard, and the thread's run stamps.

What this is not. Not a visual-design pass — the palette here is just the real tokens so nothing reads as a new direction. Every layout decision below is arguable; the structure is the proposal. Nothing here is built. /start currently renders the restored briefing minus Calendar and Your plan.

§1 · The run model

A run is the unit of work. It has five inputs. Today they live in five places with four different lifetimes, and the two that define the run — who and where — cannot be set before you start.

inputtodayproposed
audiencerail ≥xl / header <xl — thread only, absent on empty homerun bar, always visible
platformnowhere — derived from the audience rowrun bar, independent axis
skillcomposer chip + 6 starter cards (of 13 skills)composer chip — unchanged
modeldefaults from the armed skill, override in the footerunchanged, but shown only when it is a real choice
textcomposer fieldunchanged
Lifetime rule. The selector row is the setting for the next run — not a property of the thread. Changeable at any point, never retroactive. This is safe because runHeaderBlock already stamps every run with its skill, audience and platform, and each card already carries its own read anchored to thread history. The socket is pre-built: RunHeaderInput.platform exists and the routes already pass it — it is meaningless today only because there is no user choice behind it.

§3 · The merged landing

Merge means: the briefing bands move into /home's empty state. /home stays the route — it is already the landing, threads already live there, and /start stays a redirect. Nothing has to move; the empty state grows. When a thread is active the bands are gone, because they are the empty state — which is how HomeStarter already works.

§5 · Skill discoverability — three tiers, not one menu

I am revising what I proposed earlier. I said the fix was to make the skill picker the complete registry. That is not the fix. The lane handoff has it right: a skill list is a list of verbs, and users think in jobs — a 13-item menu at the front door is a poor answer to "what can this thing do."

Merging the landing collapses the first two. The third should be stated as reference-only or deleted.

§6 · The thread — run stamps make switching legible

If the selector can change mid-thread, every past run has to be able to say what it was made for. runHeaderBlock already persists that. What is missing is that the thread never renders it as provenance — it exists today only to rebuild the intro line on reload.

§7 · Still open

  1. The platform rulebook is deferred — so on day one, choosing TikTok vs Instagram changes one interpolated word in the prompt and nothing else. The control will be real before the behaviour is. Ship it anyway, or hold the control until the rulebook exists?
  2. Does the verdict move with platform? Threading platform into buildReactionPanel() is a separate build from the run bar. Until it lands, the score is identical across platforms — and a creator who switches platform and sees the same number will notice.
  3. Model as a cost control. Showing "SIM-1 Max" without a price is half a warning. The credit figures per skill are not in this sketch because I have not verified the pricing table.
  4. Greeting + composer + six cards + three bands is a long empty state. It may want the bands collapsed behind one fold, or the six cards demoted once a user has run anything.
