## How a station runs

1. Owner names the surface to dissect.
2. I drive it, capture the shot + measured facts, and read the code/DB/network behind it.
3. Owner rules on the UX; I rule on whether the backend did what the UI claims.
4. Every gap becomes a numbered finding. We do **not** fix it. We move on.

A station is DONE when every element on it has been either ticked or turned into a finding.

## Finding format

```
### F-NNN · <one-line claim>
- **Station:** · **Kind:** BACKEND | UI | UX | ICP-FIT | DATA-HONESTY | PERF | COPY
- **Severity:** blocker | major | minor | polish
- **Saw:** what actually happened
- **Expected:** what should happen, and on whose authority (spec / owner call / design system)
- **Evidence:** file:line, network call, DB row, shot path
- **Repro:** exact steps
```

*blocker* = cannot ship; path broken or lies to the user. *major* = ships but visibly wrong,
dishonest, or a dead end. *minor* = noticeable, not damaging. *polish* = craft debt.

## Findings

### F-001 · The E2E auth setup targets a route that no longer exists
- **Station:** rig · **Kind:** BACKEND (test infra) · **Severity:** minor
- **Saw:** `e2e/auth.setup.ts:33-36` waits for a URL containing `dashboard` or `welcome` after login.
  There is no `/dashboard` route in `src/app/`; login lands on `/home`.
- **Expected:** the auth fixture reflects the shipped post-login destination.
- **Evidence:** `e2e/auth.setup.ts:33`; route list under `src/app/(app)/`.
- **Repro:** `pnpm e2e:auth` with valid creds — the `waitForURL` times out at 30s.
- **Correction (measured):** `/dashboard` is not a 404 — it 308-redirects to `/home`. The fixture
  still fails, because it matches on `pathname.includes('dashboard')` and the pathname *after* the
  redirect is `/home`. So the fix is the assertion, not a missing route.
- **Note:** worked around for this audit (shared persistent browser + manual login, which also
  survives OTP). Logged because the whole Playwright E2E project depends on this fixture, so the
  suite is presumably not runnable as-is.

### F-002 · `/api/team` 500s on an infinite RLS recursion — the Team tab renders a blank page
- **Station:** S-team · **Kind:** BACKEND · **Severity:** blocker (for the feature)
- **Saw:** `/settings?tab=team` renders **nothing at all** in the panel. Three `GET /api/team`
  requests return `500 {"error":"Failed to create team"}`. Server log:
  `code: '42P17', message: 'infinite recursion detected in policy for relation "team_members"'`.
- **Expected:** either the team loads, or the UI says it failed. It currently shows an empty
  panel — indistinguishable from "you have no team", which is not what happened.
- **Evidence:** `src/app/api/team/route.ts:29-40` (auto-create path); dev log 42P17; probe
  `scratchpad/net.mjs '/settings?tab=team'`. `TeamSection` is rendered unconditionally
  (`settings-page.tsx:115`) and has **no error or empty branch**, hence the void.
- **Repro:** log in → `/settings?tab=team`.
- **Root cause is in the database, not the code:** the RLS policy on `team_members` queries
  `team_members`. Fixing needs a migration, not a component change.
- **Ask the owner first:** see F-009 — this may be a feature to delete, not repair.

### F-003 · The "$1" plan button fails silently — 503, and the user is told nothing
- **Station:** S-billing · **Kind:** UX + BACKEND · **Severity:** major
- **Saw:** clicking `Start for $1` fires `POST /api/whop/checkout` → `503 {"error":"Checkout is
  unavailable for this plan"}` (twice). **No toast, no inline error, no state change** — the button
  looks like it did nothing at all. Zero elements matching `[role=alert]`/`[role=status]`.
- **Expected:** a failed checkout says so. The known cause (no Whop keys configured) is an ops
  gap — the *silence* is the product defect, and it will survive Whop being configured.
- **Evidence:** probe `scratchpad/click.mjs '/settings?tab=billing' 'button:has-text("Start for $1")'`.
- **Repro:** `/settings?tab=billing` → click any of the three `Start for $1` buttons.

### F-010 · The audience composition bar is unlabeled and `aria-hidden` — real data rendered as ornament
- **Station:** A-audience · **Kind:** UI + UX · **Severity:** minor
- **Saw:** each audience card carries a 7px segmented strip. It encodes genuine information —
  one segment per persona, width = that persona's share, brightness = their temperature
  (cold/warm/hot). On screen it reads as a decorative grey ruler: no legend, no label, no tooltip,
  no hover. Both branches set `aria-hidden="true"`, so it is invisible to assistive tech too.
- **Expected:** the most compact factual summary of an audience should be decodable. Right now the
  only way to learn what it means is to read the source.
- **Evidence:** `src/components/audience/audience-composition-bar.tsx` (`TEMP_FILL`, `aria-hidden`).
- **Note:** the component's own doc comment argues it replaced a placeholder that "carried no
  information on any row". It now carries information nobody can read.

### F-011 · Creator Profile is a ~2,790px questionnaire — and it *is* wired (verify the ask, not the wiring)
- **Station:** S-creator-profile · **Kind:** ICP-FIT · **Severity:** major
- **Saw:** one scroll of ~2,790px covering niche + sub-genre, audience age/gender/geo/language,
  goal, creator stage, content style, cutting pace, reference creators, past wins, past flops,
  posting cadence, pain points, and video-retention consent.
- **Checked before calling it dead:** **all 19 schema fields have non-test consumers** in
  `src/lib/engine`, `src/lib/tools`, `src/lib/kc`, or `src/app/api` — `niche_primary` (23 files),
  `language` (17), `past_wins`/`past_flops`/`target_audience` (10 each), down to a floor of 3
  (`creator.ts` + `pipeline.ts` + a route) for `cuts_per_second`, `pain_points`,
  `posting_frequency`, `reference_creators`, `time_of_day_aware`.
- **So the finding is not "it's dead".** It is: (a) nothing on this screen tells the user any of it
  matters or what it changes, so the completion incentive is zero; and (b) the floor-of-3 fields
  reach the engine only as prompt plumbing — **whether they change any output is unproven and worth
  a targeted test** before we defend the length of this form.

## Deletion review — Team and Creator Profile (owner asked 2026-07-26)

### Team — **safe to delete.** Verified isolated.
- `team_id` appears in `src/types/database.types.ts` **only inside `team_members` itself** (the
  column, its FK, and the Insert/Update shapes). No other table is scoped by team; no query filters
  by it. One migration owns the whole feature: `supabase/migrations/20260217200000_teams.sql`.
- Surfaces to remove: the `team` tab + `team-section.tsx`, `use-team` hooks, `/api/team`,
  `/api/team/invite`, `/api/team/members/[id]`, and the `teams` / `team_members` tables.
- **Deleting it resolves F-002** — the recursive RLS policy goes with the table, so nobody has to
  debug a 42P17 for a feature we don't ship.

### Creator Profile — **the interview is dead; the data is live. Do not delete the data.**

The instinct is right about the *system* and wrong about the *dependency*. Both halves matter:

**1. The old 9-card interview is genuinely unreachable.** The mount chain is broken:
`ProfileInterviewModal` ← mounted only by `content-form.tsx:558` ← imported only by
`command-bar/CommandBar.tsx:7` ← **imported by nothing** (the only other mention is a comment in
`reading-chat.tsx:33`). So the modal that `profile_interview_seen_at` gates can never render.
That is dead code, and it is the system being replaced.

**2. But the profile row it wrote is read on every shipped skill, by two different paths.**

| Path | Entry | Reads |
|---|---|---|
| KC role-map | `/api/tools/{ideas,hooks,script,remix/run,react,refine,chat}` → `profileRow` → `PROFILE_ROLE_MAP` | **10 columns**: `niche_primary`, `niche_sub`, `target_audience{age_range,gender_skew,geo,language}`, `primary_goal`, `creator_stage`, `past_wins`, `past_flops`, `target_platforms`, `writing_voice_sample` |
| Video pipeline | `pipeline.ts:440` → `fetchCreatorContext(supabase, creator_handle, niche)` | the **full** set, incl. the 6 below — but keyed on `tiktok_handle`, not `user_id` |

**3. Six fields the form asks for are invisible to every generative skill.**
`content_style`, `cuts_per_second`, `reference_creators`, `posting_frequency`, `time_of_day_aware`,
`pain_points` are absent from `ProfileRow` — the type whose docstring is *"only the columns the
role-map reads"* (`profile-role-map.ts:41-54`). Only the video pipeline sees them.

**4. The single strongest field cannot be set from this form at all.**
`writing_voice_sample` drives the role-map's `voice` role, but it is **not** in the settings tab's
`GET_COLUMNS` (`api/profile/creator-profile/route.ts:16-32`). The only writer is
`profile-interview-store.ts:185` — which belongs to the dead modal. So the voice role is
unfillable by hand today.

**5. The rework already replaces that field — from real data, not a form.**
`applyCreatorPersona` backfills `writing_voice_sample` from the audience's auto-derived
`creator_persona`, "frozen at calibration from the real scrape + transcripts + omni-flash
watchNotes". It is deliberately **fallback-shaped** (manual voice wins), and gated to *calibrated,
non-General* audiences.

**So the real finding is a direction, not a delete.** The calibrated audience is already the
replacement mechanism, and it has replaced exactly one field so far. The questionnaire is the
cold-start fallback for everyone who has no calibrated audience yet.

**If we delete the tab today**, `niche_primary` (23 consumer files), `language` (17),
`target_audience`, `past_wins`/`past_flops`, `primary_goal`, `creator_stage` and `target_platforms`
lose their only manual source — and they lose it precisely for cold-start users, who are the ones
with no calibrated audience to derive from. That starves the engine at the worst moment.

**Recommended sequencing (owner's call):**
1. Delete Team now. Isolated, unambiguous, removes a live 500.
2. Delete the dead interview chain now — `ProfileInterviewModal`, `content-form.tsx`,
   `CommandBar.tsx`, `profile-interview-store.ts`, the `profile_interview_seen_at` gate. Unreachable
   code, zero risk. **This is the "old system" instinct, and it's correct.**
3. **Keep the profile data.** Cut the *form* down to the 10 fields the role-map actually reads, and
   drop the 6 that only the video pipeline consumes (or move them where they're earned).
4. Then decide the endgame: extend the `applyCreatorPersona` pattern so calibration derives niche /
   audience / goals the way it already derives voice — and retire the questionnaire when the
   derivation covers it. **Until the new onboarding writes these columns, something must.**

**Open question for the new onboarding session:** does it populate `creator_profiles`? If it does
not, this is not dead code to remove — it is a live dependency about to be starved, which is a
worse failure and an invisible one.
